# Attention map：调用图的上下文抽象

2026-10-27，依据用户对 attention 定位的澄清修订。本文记录新的方法设计；已有排序器、预测和结果保持为历史实验。本设计尚未运行端到端诊断实验。

研究目标沿用原方案：编码 Agent 最终失败后，定位最早引入且未被纠正的关键错误步骤。Attention map 的作用是组织诊断模型观察轨迹时的上下文，让相互解释的记录能够一起被阅读。

## 核心定义

原始步骤依赖图提供“哪些步骤使用了其他步骤的信息”。Attention map 将这些关系抽象成可随诊断焦点变化的上下文视图：**理解当前步骤或失败现象，需要重点阅读哪些其他步骤，以及它们为什么相关。**

记 `A[i,j | F,H]` 为在失败反馈 F 和当前诊断状态 H 下，观察步骤 i 时展开步骤 j 的优先级。它控制上下文展示、检索和阅读预算。根因判断由读取这些原始证据的诊断模型完成。相似度、访问次数和累计关注权重各自只是观察线索。

整体过程：

`轨迹与任务 → 步骤及关系索引 → 失败相关的 attention map → 上下文视图 → 诊断模型 → 根因步骤与证据`

图的执行依赖保留时间方向；诊断时可以同时阅读前因和后果。理解一次修改，往往既需要此前的约束和决策，也需要后续测试、修复和覆盖记录。

## 怎样抽象和观察

节点以原始步骤 ID 为索引，保留 thought、action、observation 的区分。概览可以压缩文本；展开后展示可回查的原始片段及其时间位置。

关系分开记录信息引用、文件或符号关联、修改与验证、纠正或替代等类型。已有图是关系来源之一；文本和实体线索用于提出补充关系。每条关系保留支持它的记录，避免把“同文件”直接等同于“同一状态”或“原因”。已有版本线索用于区分不同次修改。

观察分为三层：

1. 全局概览：保留整条轨迹的阶段、关键操作和结果，允许模型提出新的关注点。
2. 局部窗口：展开关注步骤附近的决策—操作—反馈，恢复连续语境。窗口宽度按原始 token 预算控制。
3. 关联上下文：沿关系展开远处的任务约束、文件读取、关键修改、验证和纠正记录，按原始时间标记呈现。

因此，滑动窗口是一个观察单元。高权重远程关系可以把窗口外的步骤带入视图；多窗口共享片段去重，节省的预算用于补全证据。诊断模型可以请求展开某个步骤或某类关系，由同一套预算规则执行。

首版先使用可检查的关系索引、失败锚点和固定展开规则验证这个过程。历史学习矩阵可作为后续一种关系来源进行对照。先确认上下文组织是否有效，再决定哪些关系或展开策略值得学习。

## 一个实际例子

Ansible lock 案例 `2488543283c20334` 的标注根因为第 5 步。该步使用 acquire/release，而最终失败测试检查上下文管理器的 `__enter__` 调用。第 2 步还有一个后来被恢复的工具参数错误。

围绕第 5 步生成的视图，应当把锁操作代码、相关需求、最终断言和后续纠正情况一起交给诊断模型。这样模型能比较“实现了怎样的调用语义”与“测试要求怎样的调用语义”，并查看第 2 步的异常是否已经恢复。

这也说明关注与归因的区别：最终断言可以获得很高的阅读优先级，它为判断更早的修改提供依据。观察重点可以落在验证记录上，最终答案仍指向更早引入错误的步骤。

## 现有实验放在什么位置

已有 v1 和 semantic v2 将 attention 聚合结果直接用于监督根因排序，回答的是关系特征能否帮助小模型排序。它们尚未检验“调用图的上下文抽象能否帮助同一个诊断模型观察轨迹”。

此前的 Top-5 命中说明一些根因进入了候选集合；它不直接衡量解释根因所需的其他证据是否同时呈现。此前窗口试验修改的是排序器内部的矩阵，新的窗口试验应修改诊断模型实际看到的上下文。

All-at-Once 的价值在于提供完整上下文读取的参照。其命中案例提示原始文本中存在可用的判别信息。新的假设是：关系组织能够在有限阅读预算下保留这些信息，并帮助模型比较原因、后果与恢复过程。它是否提高准确率需要下面的端到端对照。

## 最小对照实验

固定同一个诊断模型、thinking 配置、根因定义、任务与失败反馈，以及输出格式。上下文选择过程不读取根因标签、标注原因或 gold patch。分别运行：

| 条件 | 诊断模型读取的上下文 | 作用 |
|---|---|---|
| All-at-Once | 按时间排列的完整轨迹 | 完整上下文参照，单独记录实际 token 成本 |
| 窗口/文本检索 | 相同预算下的局部窗口与文本相关片段 | 检查简单聚焦能够做到什么 |
| 原调用图 | 相同预算下沿已有边展开的原文 | 检查固定关系提供的上下文 |
| Attention map | 相同预算下按关注关系组织局部与远程原文 | 检查新的上下文抽象 |

再给 attention map 增加一个“同事实、不同呈现”对照：固定选中的原始片段集合，一份按时间平铺，一份按关系组织。两份使用相同的步骤 ID、任务、失败反馈和诊断指令，记录关系标记的额外 token。这样可以区分选取了更好的材料与材料组织本身的作用。

先固定一次上下文构建、一次诊断调用，隔离上下文组织效果；再比较允许多次展开的版本。总预算包含构图、选择、诊断和追加展开，缓存成本与首次运行成本分别报告。需要等总预算比较时，对所有方法应用预先固定的预算上限，完整 All-at-Once 另保留为全量参照。

主要结果仍是最终诊断的 Top-1、Top-5、MRR，以及调用次数、总 token、延迟。机制分析记录：根因原文是否被展示、关键约束和验证是否共同出现、恢复记录是否丢失、根因已经展示时模型能否判断正确。证据链覆盖需人工审阅支持，不能只用根因单步覆盖代替。

先用 Ansible lock、OpenLibrary 和 qutebrowser 的已有错例检查视图能否保留判别所需的原文；这一步只检查机制。随后在固定的开发集上运行同模型对照，按仓库进行配对统计。已有 102 条开发数据上的结果用于设计验证，后续独立数据评估沿用原计划。

## 与原 RQ 和汇报衔接

RQ1：这种上下文组织能否改善最终根因定位？

RQ2：局部连续性、远程关系以及验证/恢复上下文分别贡献多少？同事实对照检验组织方式本身。

RQ3：在相同总预算下，准确率、阅读成本与重复运行稳定性如何变化？

汇报主线可以表述为：**我把调用图抽象成面向诊断的 attention map，让模型围绕一个可疑步骤，同时看到相关决策、执行结果和后续验证，研究这种上下文组织能否帮助它更准确、更省成本地定位最早的关键错误。**

展示顺序：同一个失败案例 → 全文阅读与原调用图提供的视图 → 新 map 如何组织同一批证据 → 固定诊断模型的对照结果。历史小模型排序结果作为前期探索，端到端上下文实验另列。
